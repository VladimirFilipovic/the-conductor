# v2 — WASM Plugin Architecture

## Idea

Make the engine pluggable by moving host-side actions behind WASM modules. The
engine stays the orchestration brain (decide placement, drive lifecycle,
self-heal); the *how* of talking to a given host kind lives in a WASM plugin the
engine loads at runtime.

## Plugin architecture using WASM

- Host communication ("agent hosts" — the builders/runners that actually start,
  stop, and report replicas) sits **behind** WASM modules the engine executes.
- We hand the engine the **paths to these `.wasm` files** (config) and it uses
  them during orchestration instead of having host protocols hardcoded.
- Each plugin is a self-contained module implementing a known set of exported
  functions. Adding support for a new host backend = drop in a new `.wasm`, no
  engine rebuild.

## Builder / host communication behind WASM

- The orchestration loop already splits into Sensor (observe) and Orchestrator
  (decide/act). Plugins are the **act** boundary: when the Orchestrator decides
  "start this replica on that host", it invokes the host's WASM plugin to carry
  it out.
- The plugin owns the host-specific wire protocol (SSH, agent RPC, container
  API, etc.). The engine never speaks it directly — it only speaks the WASM
  contract.

## Execution model

- Engine **executes the WASM module** to tell the host what to do.
- Inputs and outputs are **predefined params** — a fixed schema both sides agree
  on, so the engine can marshal a request in and read a structured result out
  regardless of which plugin handles it.
- Candidate operations to expose as plugin entry points (map onto existing
  store/lifecycle actions):
  - `start_replica` — given a ReplicaSpec + host binding, launch it.
  - `stop_replica` / `drain` — graceful shutdown for rollout/reclaim.
  - `observe` — return replica phase/health/restart counts (feeds the Sensor).
  - `heartbeat` — host liveness.
- Predefined I/O (sketch): input = serialized spec (deployment, region, cpu/mem,
  volume binding, desired status); output = result struct (phase, healthy,
  exit reason, error).

## Why WASM

- Sandboxed: a buggy/hostile host plugin can't reach engine internals or the
  control-plane DB.
- Language-agnostic: plugins can be written in anything that compiles to WASM.
- Hot-swappable: ship new host backends without redeploying the engine.

## Open questions

- Host/runtime: wazero (pure Go, no cgo) vs wasmtime bindings.
- I/O encoding across the boundary: JSON vs protobuf vs WIT/component model.
- Capability/host-function set the engine grants each plugin (network, fs, time).
- How plugins are registered & versioned, and contract compatibility checks.
- Sync request/response vs streaming for long-running ops (rollout, drain).
