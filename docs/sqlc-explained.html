How sqlc is used in this project

Hand-written SQL → type-safe Go, with the goose migrations as the single schema source of truth.

You write plain SQL in db/queries/*.sql and a DDL schema in db/migrations/*.sql. sqlc generate reads both, type-checks every query against the schema, and emits Go structs + methods into internal/storage/db/. You never hand-write the scanning/parameter-binding boilerplate, and a query that references a non-existent column fails at generate time, not at runtime.

1 · Configuration

sqlc.yaml

version: "2"
sql:
  - engine: "postgresql"
    schema: "db/migrations"        # reuse goose migrations as schema-of-truth
    queries: "db/queries"          # where the named queries live
    gen:
      go:
        package: "db"
        out: "internal/storage/db"
        sql_package: "database/sql" # generate against database/sql, not pgx
        emit_json_tags: true        # `json:"..."` tags on every struct field
KeyEffect
schemaPoints at the goose migration dir. sqlc parses the CREATE TABLE DDL to learn column types. goose's -- +goose markers are tolerated.
queriesDir of .sql files, each holding one or more annotated queries.
sql_package: database/sqlEmitted methods take a DBTX built on database/sql, so the standard pool + pgx stdlib driver work underneath.
emit_json_tagsWhy every generated struct field carries a snake-case json: tag.

2 · Defining a query

A query is plain SQL with a magic comment: -- name: MethodName :returnkind. The $1, $2 … placeholders become method parameters.

db/queries/records.sql

-- name: InsertRecord :execrows
INSERT INTO records (collection, key, data)
VALUES ($1, $2, $3)
ON CONFLICT (collection, key) DO NOTHING;

-- name: GetRecord :one
SELECT data
FROM records
WHERE collection = $1 AND key = $2;

The :returnkind annotations used here

AnnotationGenerated returnUsed for
:onesingle row → struct (or single column → that type)GetRecord, all the Create* / INSERT … RETURNING * queries
:execrows(int64, error) — rows affectedInsertRecord, UpdateRecord, DeleteRecord

The project leans on :execrows deliberately: InsertRecord uses ON CONFLICT DO NOTHING, so rows == 0 means "key already taken" — detected without a separate existence probe racing the write.

Two parameter shapes

If a query has one parameter, the method takes it directly. With multiple, sqlc bundles them into a generated ...Params struct:

// one param → scalar argument
func (q *Queries) CreateProject(ctx, name string) (Project, error)

// multiple params → a Params struct
func (q *Queries) GetRecord(ctx, arg GetRecordParams) (json.RawMessage, error)
type GetRecordParams struct { Collection string; Key string }

Example: source → generated method

// from GetRecord above, sqlc emits:
func (q *Queries) GetRecord(ctx context.Context, arg GetRecordParams) (json.RawMessage, error) {
    row := q.db.QueryRowContext(ctx, getRecord, arg.Collection, arg.Key)
    var data json.RawMessage
    err := row.Scan(&data)
    return data, err
}

4 · How the app consumes it

internal/storage/postgres.go

PostgresClient holds a *db.Queries built from the database/sql pool, and wraps each generated method — translating Go values to/from JSON and mapping DB errors onto the package's sentinel errors.

type PostgresClient struct {
    pool    *sql.DB
    queries *db.Queries
}

func NewPostgresClient(ctx, dsn string) (*PostgresClient, error) {
    pool, _ := sql.Open("pgx", dsn)   // pgx stdlib driver under database/sql
    ...
    return &PostgresClient{pool: pool, queries: db.New(pool)}, nil
}

// rows == 0 from ON CONFLICT DO NOTHING ⇒ key already taken
func (c *PostgresClient) Insert(ctx, collection, key string, v any) error {
    data, _ := json.Marshal(v)
    n, err := c.queries.InsertRecord(ctx, db.InsertRecordParams{...})
    if n == 0 { return fmt.Errorf("%s/%s: %w", collection, key, ErrExists) }
    return err
}

For the control-plane creates, a unique-constraint violation (SQLSTATE 23505) from INSERT … RETURNING * is caught via uniqueViolation() and mapped to ErrExists — again no separate existence query.

5 · Regenerating

Makefile

sqlc:
	sqlc generate     # install once: brew install sqlc
Workflow when you change the DB:
  • Add/edit a migration in db/migrations/ (schema change).
  • Add/edit the query in db/queries/.
  • Run make sqlc → regenerates internal/storage/db/.
  • Run make migrate (goose) to apply the DDL to a running DB.
  • Wrap the new generated method in PostgresClient if it needs error mapping.

sqlc never touches a live database — it type-checks queries against the migration DDL statically. goose is the only thing that talks to a running Postgres.
