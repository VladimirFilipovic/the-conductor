Engineering Requirements Document

Orchestration Engine for Stateless & Stateful Compute Workloads

Author: Vladimir Filipović Status: Draft / Interview pre-work Date: 2026-06-07 Scope: Control-plane design + minimal runnable core

The engine that takes a user's desired state for a service and continuously reconciles it onto a fleet of machines — handling placement, deploy lifecycle, health, rollouts, self-healing, and the hard split between fungible stateless replicas and volume-pinned stateful workloads.

Grounding. Modeled on how Railway actually runs: own bare-metal fleet (“Railway Metal”, 4 regions), workloads in micro-VMs/containers, Temporal-driven provisioning + a metal control plane, BGP-unnumbered networking, zero-downtime deploys via healthcheck + overlap/drain, and volumes for state. This ERD designs the workload orchestrator that sits above that fabric.

1Problem & Context

A PaaS lets a developer push code and get a running, networked, observable service with zero infra work. Between "image built" and "service serving traffic" sits the orchestration engine. It must:

  • Decide where each workload runs across a heterogeneous multi-region bare-metal fleet (bin-packing under CPU/RAM/volume/region constraints).
  • Drive each deploy through a lifecycle: schedule → start → health-gate → shift traffic → drain old → reclaim.
  • Self-heal: detect dead replicas/hosts and reconcile back to desired state.
  • Treat stateless and stateful workloads with fundamentally different placement & rollout rules.
  • Be declarative and level-triggered — survive control-plane restarts, never lose track of reality.

2Goals & Non-Goals

Goals

  • Declarative desired-state API; continuous reconciliation.
  • Constraint-aware scheduler (resources, region, volume affinity, anti-affinity, spread).
  • Zero-downtime rollouts (overlap + drain) with automatic rollback on failed health gate.
  • Correct stateful handling: single-writer volume guarantee, controlled migration.
  • Self-healing on replica + host failure; safe host drain.
  • Crash-safe control plane (durable state, idempotent workflows).

Non-Goals (v1)

  • The build pipeline (assume an image/OCI artifact already exists).
  • L7 ingress / TLS / DNS internals (assume a routing mesh + service discovery hook).
  • Autoscaling policy engine (expose hooks; ship fixed replica counts first).
  • Multi-cloud / cross-region replication of data (volume = single region in v1).
  • Billing, quotas, auth (assume an upstream API gateway).

4Stateless vs Stateful — the core distinction

stateless

  • Replicas are fungible — any host with capacity works.
  • Scale = add/remove replicas freely; spread across hosts/regions.
  • Rollout: create new, then destroy old (surge). Cheap, parallel.
  • Host failure → just reschedule elsewhere.

stateful

  • Replica is pinned to its Volume's host (data has gravity).
  • Single-writer invariant: never two writers on one volume.
  • Rollout: stop old, then start new on same host (recreate), or orchestrated volume hand-off. Brief downtime unless replicated.
  • Host failure → can't "just reschedule"; needs volume reattach/restore + fencing.
Design consequence: placement and rollout strategy are policy objects keyed on stateful: bool. Same reconciler, two strategies. This is the single most important modeling decision and the thing I'd demo live.

4bProvisioning & scaling stateful workloads

Adding a stateful workload is volume-first: the data exists before the replica, and the disk's location — not the scheduler's free choice — decides where the replica runs.

USER: add service "pg" stateful volume=10GB region=us-west │ ▼ 1. PROVISION VOLUME scheduler picks a host with disk capacity in us-west vol-abc → { host:A, region:us-west, size:10GB, lease:none } │ the volume now has an IDENTITY and a LOCATION ▼ 2. PLACE REPLICA NOT free — replica is PINNED to host A (where vol-abc lives) │ filter rule §6: "host must hold the bound volume" ▼ 3. ACQUIRE LEASE replica takes a single-writer lease on vol-abc vol-abc.lease = pg-0 ← no one else may mount it read-write (anti split-brain) │ ▼ 4. ATTACH + MOUNT + START container mounts vol-abc at /data, then boots │ ▼ 5. HEALTH-GATE → ACTIVE + STABLE identity (pg-0.internal) so peers/clients find THIS one

Three things differ from stateless, each one line:

  • Placement is determined, not chosen — once the volume exists, the replica must go where the volume is.
  • Single-writer lease (step 3) — the safety invariant; stops two replicas ever writing the same disk (corruption).
  • Stable identity — a fixed name (pg-0), not a slot behind a load balancer, so clients/peers address a specific instance.

Scaling — the part people get wrong

You cannot add interchangeable copies like stateless — each instance needs its own data. Scaling stateful = N distinct instances, each with its own volume and stable name (pg-0, pg-1, …) — what Kubernetes calls a StatefulSet.

Key boundary: the orchestrator does not replicate data — it only guarantees stable identity + stable volume binding per instance. Replication is the app's job (Postgres streaming, Raft, etc.). Most stateful workloads run as singletons (replicas=1); HA lives inside the app via leader election. So "add a stateful workload" usually = provision 1 volume + run 1 pinned, named replica.

The fork that decides the failure story: where does the disk live?

BackingAdd / fail-over behavior
Local NVMe (disk physically in host A)Fast, but truly pinned. Host A dies → can't reschedule; wait for A to return or restore from snapshot/backup. Maximum data gravity.
Networked / replicated block storageVolume can detach from A, reattach to B. Host death → fence the dead host's lease, wait for it to expire, then reattach elsewhere. Survives host death; slower & more complex.

This choice dictates §8's failure handling: local disk → "wait/restore"; networked → "reattach after fence." Either way, never reattach while the old writer might still hold the lease.

Railway: volumes are bound to a region; railwayapp/vol-unpacker literally unpacks a tarball into a Railway volume — how they seed volume data.

Volume resize — coordinate, don't implement

The orchestrator owns volume.size as a desired-state field and reconciles drift, but delegates the actual grow to a storage driver behind an interface — the same seam as the runtime (don't implement Firecracker) and network (don't implement Envoy).

type VolumeStore interface {
    Provision(spec) (Volume, error)
    Attach(v, host) error
    Detach(v) error
    Resize(v, newSizeGB) error   // ← grow block device + extend filesystem; provider-specific
}
  • Grow-only, in-place — unlike most fields (create/destroy to converge), resize mutates an existing resource. So the reconciler special-cases it: desired.size > actual.size → Resize; desired.size < actual.size → reject (shrinking risks data loss).
  • Online & coupled to the running replica — it happens while the workload holds the single-writer lease; "grow device" then "extend FS" is a two-step with its own failure modes → a good fit for a small durable workflow (retry/rollback).
  • v1 scope: model the field + the Resize hook (FakeVolumeStore just bumps a number); real device/FS growth is delegated and out-of-scope — exactly like networking.
Mechanism vs policy. Resizing is mechanism (engine coordinates, driver executes). Auto-growing at 80% disk is policy — a separate controller that patches volume.size, same as an autoscaler patches replicas (§2 Non-Goals). The engine stays policy-agnostic; any client (human, GitOps, autoscaler) drives it by patching desired state.

★Reference: how Railway actually does this

Railway has publicly described its orchestrator. It is a custom, Temporal-based engine — explicitly not Kubernetes. This ERD is modeled on it; the mapping is near 1:1. Below is their real flow from railway up to a running, scaled, self-healing service.

What is Temporal? A durable workflow engine. You write a long multi-step process as ordinary code (a workflow) that calls side-effecting steps (activities). Temporal persists every completed step, so if the server crashes mid-deploy it replays history and resumes exactly where it left off — variables intact. Failed steps auto-retry; timers/timeouts/cancel are built in. A deploy is a durable workflow — that's why Railway (and this ERD) build on it instead of hand-rolling a crash-safe state machine.
railway up / git push │ ▼ ┌─────────────────────────┐ Temporal workflow #1 │ BUILD workflow │ build Docker image → push to internal registry └───────────┬─────────────┘ ▼ ┌─────────────────────────┐ Temporal workflow #2 (the orchestration brain) │ DEPLOY workflow │ decides: which region? which "stacker" (host)? │ │ how many replicas? → fans out sub-workflows └───────────┬─────────────┘ ▼ ┌─────────────────────────┐ one SUB-workflow per replica │ place replica on stacker│ (a "deployment instance" = repeatable copy of the spec) │ assign unique IPv6 │ └───────────┬─────────────┘ ▼ ┌─────────────────────────┐ event-based, over gRPC, propagates in milliseconds │ NETWORK CONTROL PLANE │──► Envoy proxies (public: CDS round-robin LB) │ (custom Go) │──► DNS servers (private: AAAA records, random IPv6 pick) └───────────┬─────────────┘ ▼ healthcheck endpoints gate "ready" ──► replica crashes? network FAILS OVER automatically
Fan-out / fan-in. The deploy workflow doesn't start replicas one-by-one — it fans out one sub-workflow per replica (parallel), then fans in (waits for all healthy) before completing. Railway, under "🎻 Orchestrating replicas": "To start the deployment of the replica containers on the selected stackers, we then trigger sub-workflows. These are basically multiple copies of the same one we had in place before introducing replicas." — i.e. they scaled the original single-deploy workflow to N replicas by running N copies in parallel, no rewrite.

6Scheduler Design

Per unplaced Replica:

  1. Filter (hard): host region == required region; free CPU/RAM ≥ request; if stateful → host must hold the bound Volume (or be able to attach it); anti-affinity not violated; host Ready.
  2. Score (soft): bin-pack (prefer fuller hosts to reduce fragmentation) vs spread (prefer emptier hosts for HA) — weighted; penalize hosts already running a replica of the same Deployment (spread).
  3. Bind: atomically reserve resources in the store (optimistic concurrency / version check) so two scheduling passes can't double-book a host.
Stateful shortcut: a stateful replica with an existing bound volume skips scoring — its placement is determined by where the volume lives. The scheduler only chooses freely on first placement or during an explicit migration.

7Deployment Lifecycle (state machine)

PENDING ─► SCHEDULING ─► STARTING ─► HEALTH_CHECK ─┬─► HEALTHY ─► SHIFTING ─► ACTIVE │ │ │ │ (fail/timeout) (superseded) ▼ ▼ ▼ FAILED ◄──────────────── ROLLBACK ◄────────────────┘ DRAINING ─► REAPED

Stateless rollout (surge)

  1. Schedule + start N new replicas alongside old.
  2. Gate on healthcheck (configurable path/timeout). Fail ⇒ tear down new, keep old, mark FAILED.
  3. Shift traffic to new (update routing mesh / service discovery).
  4. SIGTERM old replicas, allow drain_seconds for in-flight requests, then reap.

Stateful rollout (recreate / hand-off)

  1. Stop old writer, fence it (revoke volume lease) — enforce single-writer.
  2. Detach volume; attach to new replica's host (same host in the common case).
  3. Start new replica, health-gate, then admit traffic. Rollback = re-attach to old image.

8Self-Healing & Failure Handling

FailureDetectionResponse
Replica crashAgent reports exit / failed healthcheckReconciler sees desired>observed → reschedule (stateless) or restart-in-place (stateful).
Host downMissed heartbeats > threshold → host NotReadyStateless replicas rescheduled elsewhere. Stateful: wait for fence/lease expiry before reattaching volume elsewhere — never split-brain.
Control-plane restart—State in Postgres + Temporal histories; reconciler rebuilds from observed truth, in-flight rollouts resume. No work lost.

Partial starts — "what if only 2 of 3 come up?"

This is why the engine is level-triggered, not "fire 3 and await all" (which loses track if the control plane dies after firing 2). The loop doesn't care why there are 2 — next tick it sees desired=3, actual=2 and starts the missing one. The only real decisions are why the third failed and whether the deploy completes:

Cause / phaseResponse
Unschedulable (no host capacity)Replica stays PENDING, retried each tick; surface insufficient capacity. Comes up when room appears.
Started but crash-loops / fails healthRestart with backoff + max-retries cap (restartPolicyType / maxRetries). After cap → mark replica FAILED, stop hammering.
Initial deploy / rollout, fan-in waitingWait for all healthy up to healthcheckTimeout. Timeout → deploy FAILED; for a rollout, auto-rollback to old version (never half-cut-over).
Steady state, 1 of 3 diesServe on the healthy 2 (degraded, not down) while the loop restarts the 3rd. Router only sees healthy replicas → failover is automatic.
Two correctness rules: (1) Idempotency — key on replica identity ("start r3 of d-v2") and record what's started, or a post-crash retry spawns a 4th. (2) Don't fail the whole deploy on one slow replica — gate on minReady + timeout, not strict all-or-nothing forever.

Networking — stubbed behind an interface

Railway built a real custom Go control plane (assign IPv6 → push to network control plane → propagate to Envoy + DNS over gRPC, ms-fast). For v1 we model the behavior, not the wires — same trick as the runtime. FakeNetwork is an in-memory table; a DockerRuntime variant could return real container IPs.

type Network interface {
    Register(svc, replica, addr)   // replica now reachable (assign fake IPv6/addr)
    Deregister(svc, replica)        // remove from rotation
    Resolve(svc) []addr             // healthy endpoints — service discovery
    Route(svc) (addr, error)        // pick one — round-robin / random
}

Only two behaviors matter — and each buys a whole feature for free:

  • Health-gated registration — call Register only when a replica turns HEALTHY, Deregister the instant it fails/drains. ⇒ Resolve only ever returns healthy endpoints, so killing a replica fails traffic over automatically, no extra code.
  • Atomic swap on rollout — register all v2, then deregister all v1 in one move. ⇒ traffic shifts from v1's endpoint set to v2's (step 4 of §7). Rollback = swap back.

Maps to Railway 1:1: Register/Deregister ↔ orchestrator pushing/removing an IPv6 in the network control plane; Resolve/Route ↔ Envoy CDS round-robin + DNS AAAA records.

10Tech Choices

Go — control plane & agent Postgres — desired/observed state Temporal — durable rollout workflows gRPC streaming — CP ⇄ agent micro-VM / OCI — isolation level-triggered reconcile

Why durable workflows (Temporal): a rollout is a long, multi-step, failure-prone process that must survive control-plane crashes and never get stuck half-done. Encoding it as a workflow gives retries, timeouts, and exactly-once-ish semantics for free — Railway uses Temporal for exactly this class of problem in their metal provisioning.

13Public Interface — how a user drives the engine

The user never talks to the orchestrator directly. They use a CLI that is a thin client over a GraphQL API (this mirrors Railway exactly — their CLI does no orchestration; it only expresses intent, and the backend's workflows do the work). The interface is declarative: you don't command actions, you commit a new desired state and the reconciler closes the gap.

The key principle: a deploy is a "commit" to desired state

Railway's scale sends a mutation literally named EnvironmentPatchCommit — a patch + a commit message:

EnvironmentPatchCommit {
  environment_id,
  patch,                            // multiRegionConfig: { region → numReplicas }
  commit_message: "Scale my-api",   // ← desired-state changes are versioned, like git
}

You don't say "start 2 containers." You commit a new desired state, and the orchestrator reconciles reality to it. This is the same model as §14 below — just made auditable.

How up knows which state to achieve

up uploads code, not a replica count — so the target state is merged from three layers:

  1. Context — which service/environment (from the local link file or --service/--environment). Picks whose state to patch.
  2. Config-as-code — railway.json / railway.toml in the repo: the declarative deploy spec.
  3. Stored settings — env vars, volumes, and anything not overridden above (or set by a prior scale).
// railway.json — the declarative desired state committed alongside code
{
  "build":  { "builder": "RAILPACK" },
  "deploy": {
    "startCommand": "node server.js",
    "numReplicas": 2,
    "region": "us-west1",
    "healthcheckPath": "/health",
    "healthcheckTimeout": 300,
    "restartPolicyType": "ON_FAILURE"
  }
}

up changes only the image axis (builds a new image, makes a new deployment instance); replicas/region come from this file or a prior scale; env from stored settings. The orchestrator reconciles to the merged whole.

Design enhancement (worth pitching live): because every change is a commit to desired state, rollback is just re-applying the previous commit. Make the desired-state store append-only & versioned — you get auditability, instant rollback, and a clean answer to "what changed and when" for free.
Mental model: desired state is one object — { image, replicas, region, env, volume, healthcheck }. Different commands patch different fields; one reconcile loop drives them all. That's why "deploy", "scale", "rollback", and "self-heal" aren't separate subsystems — they're the same loop reacting to a patched field.

14Worked Example — the engine driving the runtime

This shows how the pieces actually interact at runtime: the engine never touches a machine directly — it only ever calls the Runtime interface, and only ever reacts to what the runtime reports back. Everything below is one continuous control loop.

The contract (what the engine is allowed to do)

type Runtime interface {
    Start(r ReplicaSpec) (Handle, error)  // launch one copy of a replica
    Stop(h Handle, drainSecs int) error    // SIGTERM, wait drainSecs, then kill
    Health(h Handle) Phase                  // STARTING | HEALTHY | EXITED | FAILED
    List() []Running                        // ground truth: what's actually alive
}
// FakeRuntime (demo) = goroutines.   DockerRuntime (flex) = containers.
// The engine code is IDENTICAL for both — that's the whole point of the interface.

The loop that uses it (the reconciler)

for {                                          // runs forever, every ~1s
    desired := store.DesiredReplicas(service)  // e.g. "I want 3 of v2"
    actual  := runtime.List()                  // what's really running

    // 1. MISSING — desired but not running → schedule + Start
    for _, r := range missing(desired, actual) {
        host := scheduler.Place(r, fleet)       // filter → score → bind
        if host == nil { log("unschedulable"); continue }
        h, _ := runtime.Start(r.On(host))       // ← engine touches reality HERE
        store.Record(r, host, h)
    }

    // 2. SURPLUS — running but no longer wanted (old version) → drain + Stop
    for _, h := range surplus(desired, actual) {
        runtime.Stop(h, service.DrainSeconds)   // graceful
    }

    // 3. UNHEALTHY — running but failed its check → forget it; next loop re-Starts
    for _, h := range actual {
        if runtime.Health(h) == FAILED { store.Forget(h) }
    }

    sleep(1 * time.Second)
}
Why this is the whole design: there's no "deploy()" command that imperatively marches through steps. You just change desired (3→5 replicas, v1→v2) and the same loop closes the gap. Scale, deploy, rollback, self-heal are all the same code path reacting to a changed goal or a changed reality.

15The Chaos CLI — the simulation harness

Everywhere above I trace behavior "in the chaos CLI." This is what it is: not part of the orchestrator — the test harness wrapped around it. It's a wind tunnel. The engine + reconcile loop (§14) is the real system under test; the CLI plays the two roles the real world would otherwise play and narrates the loop so a human can watch desired vs observed converge.

Role 1 — the user / API

  • Turns typed commands (deploy, scale, kill) into desired-state patches on the store — exactly the §13 commands, minus GraphQL.
  • It never commands actions; it only commits intent. The loop does the rest.

Role 2 — the compute layer

  • Provides the FakeRuntime (§14) — goroutines pretending to be containers, so no Docker/Firecracker needed to demo the logic.

How a human drives it — the tick loop

Two input channels, one loop. Each tick the engine does one pass of §14: observe (List()) → diff (desired − observed) → act on the gap (Start/Stop/forget) → print. A human either:

  • Steps it — tick / press enter to advance one tick at a time and read each decision. Best for explaining the algorithm (the t0…t10 trace in §14 is exactly this).
  • Free-runs it — auto-tick every ~1s; you just type commands + chaos while it self-heals live.

Why the harness is the proof, not the product. Because the engine only talks to the Runtime interface, the CLI's FakeRuntime and a future DockerRuntime are interchangeable — same engine, swap the backend. And chaos injection is the cleanest possible demo of correctness: kill r2 (t5) drives the engine down the identical code path as a user-requested scale (t3) — the loop doesn't care why observed ≠ desired, it just closes the gap. That equivalence is the whole declarative, level-triggered claim made visible. The "tracking what's going on" is just the loop dumping its state each tick; turn the printing off and the same engine runs in production.

BScheduler — decisions, rationale & interview prep

The placement story is the richest discussion surface (§6, §12). These are the calls made and why, plus the questions an interviewer is likely to push on and crisp answers.

Decisions & why

DecisionWhy
Centralized scheduler — one active writer of placements, one elected leader per region. Makes the bind the single writer of allocations ⇒ no double-booking without distributed locking. Reconcilers stay dumb gap-detectors. Industry norm (k8s, Borg).
Reconciliation parallel, sharded per project-service. Each service owns disjoint rows (deployments/replicas) ⇒ no cross-service contention; parallelism buys throughput. The same service reconciled twice at once is prevented by a per-key workqueue (one in-flight per service) + a per-service lease when the control plane is HA.
Split reconciler from scheduler — reconciler emits an unplaced replica; the central scheduler does filter→score→bind. Funnels all competition for shared host capacity into the one writer; reconcilers never choose a host. This is the Kubernetes controller/scheduler split.
Optimistic concurrency on the bind (revision CAS / SELECT … FOR UPDATE on the host row). Safety net for when >1 actor mutates placement (multiple schedulers, or scheduler + self-heal firing together). With a single regional scheduler it's belt-and-braces, not load-bearing — but cheap insurance.
Leader election for the scheduler (HA). Multiple processes, one active. Removes the SPOF; failover in seconds; only new placements pause during the gap — running workloads are untouched because scheduling is off the data path.
Scale out by sharding the pool — one scheduler per region, never multiple schedulers over one shared pool. Preserves "single writer per resource pool" (a us-west and an eu placement never contend) while scaling horizontally. How Google (many Borg cells) and k8s (many clusters) actually scale.
Level-triggered reconcile (not edge-triggered). Recompute from a full-state snapshot each tick; can't lose track if a status event is missed or reordered. Transient desired ≠ observed is normal — converge, don't react per-event.
"Leader election" = multiple Go processes, one active. You run N replicas of the control-plane binary (ideally on separate nodes, separate failure domains). They race to acquire a lease; the winner is the active scheduler, the rest idle as hot standbys and keep trying. If the leader's process dies or fails to renew, the lease expires and a standby takes over. In this stack the lease is cheap to build on what we already have: a Postgres advisory lock / a leases row with a TTL heartbeat, or a singleton Temporal workflow (workflow-id dedup gives "exactly one" for free). Goroutines within one process don't count — a single process dying takes them all, so they give parallelism, not availability.

Likely interview questions & answers

QuestionAnswer
Is a single scheduler realistic in production? Yes — one active leader + hot standbys is the norm. k8s runs ~5k nodes / 150k pods on one active kube-scheduler; a Borg cell (~10k machines) on one Borgmaster. Our 60k deploys/hr ≈ 17/s — trivial. Scale by regional sharding, not by stacking schedulers.
Isn't one scheduler a SPOF? No — leader election; a standby grabs the lease in seconds; running workloads are unaffected. Separate availability (leader election) from throughput (fast scheduler + sharding); conflating them is the mistake.
Do parallel per-service reconcilers compete? Not on their own state — sharding by service partitions the rows. They compete only for shared host capacity, and that's resolved by routing every bind through the single scheduler. Same-service double-run is stopped by a per-key workqueue + lease.
You bin-pack on state that's stale a moment later — race? Scoring is a hint on a possibly-stale read; the bind is an atomic CAS that re-checks fit inside a txn (loser re-scores). Reality is the final judge — a failed Start just means the next tick reschedules. Idempotency keyed on replica identity ("r3 of d-v2") makes retries safe.
Edge- or level-triggered, and why? Level. Recompute from current full state each pass; robust to missed/reordered events. Edge-triggered loses track the moment one event is dropped.
How would you scale past one scheduler on a single pool? The Omega model: many schedulers over shared state with lock-free optimistic concurrency — that's where the bind CAS becomes load-bearing. Nomad ships this (parallel scheduler workers + a plan queue serialized at the leader). Hyperscale only.
What's different about scheduling stateful workloads? Placement is determined, not chosen — the replica must go where its volume lives; the single-writer lease enforces it; the scheduler skips scoring once the volume is bound (§4, §6).
