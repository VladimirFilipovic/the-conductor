Reconciliation Strategy

How the engine drives the live fleet toward what the user declared — one level-triggered tick at a time.

① The core idea ② Built vs designed ③ Observe · Decide · Act ④ The snapshot read-tx ⑤ Target vs outgoing ⑥ Replica lifecycle ⑦ Rolling vs recreate ⑧ One reconcile tick ⑨ Losing races safely ⑩ Convergence

①The core idea

Postgres is the single source of truth. Every tick the scheduler reads desired state (what the user declared) and observed state (what the fleet actually is) in one frozen snapshot, computes the gap, and emits the minimal set of writes to close it. No in-memory state machine, no hidden assumptions — the loop is level-triggered and declarative, so a slow, skipped, or crashed pass simply self-heals on the next one.

Two goroutines, one DB

The engine launches a Sensor (writes observed reality back to the DB) and a Scheduler (reads desired+observed, writes intents). They never talk directly — they coordinate through the database.

internal/engine/engine.go:8 — go sensor.tick(ctx); go scheduler.tick(ctx)

Idle gap, not a fixed cadence

A pass runs fully to completion, then the loop idles reconcileInterval (2s) before the next. Passes never overlap — single goroutine, sequential.

④The snapshot read-tx — why one frozen instant

Desired and observed are read in a single REPEATABLE READ, read-only transaction. Both halves of the diff observe the same instant, so they can't drift between queries and tear the comparison. It's read-only — takes no row locks, exists only to pin the snapshot — so it always rolls back.

⑤How "new" is told apart from "old"

For every desired row, the scheduler builds a replicaGroup keyed by (environment_service_id, region), then splits the bucket on is_current:

is_current = true → TARGET

The new version you're converging toward. The scheduler scales these up to desired_replicas and health-gates them.

is_current = false → OUTGOING

Old replicas still running under a superseded deployment. The scheduler drains then reaps these once the new side is healthy.

⚠ Subtle but critical

The discriminator is is_current, not replicas.revision. revision is the CAS counter for the Sensor↔Scheduler race — it has nothing to do with deployment version. A partial unique index one_current_deployment_per_service guarantees exactly one current commit per service.

⏱ drain_seconds — the graceful window (default 30s)

On IntentDrain the engine sets phase=draining and stamps drained_at. The draining → reaped transition fires only after the full window elapses — even if the container already stopped. Why wait? A stale load-balancer routing entry could still send new requests to a dead replica; waiting guarantees the LB has converged first. drain_seconds=0 → reap immediately (fine for stateless services where the LB converges fast).

🧊 status=failed → rollout freezes, no auto-rollback

When a new replica trips restart_max (default 5): replica → failed (terminal), deployment → failed, and the old version keeps serving — the new one never takes over. The engine does not auto-rollback; failed is a signal column for the operator. Exit paths: conductor rollback (re-point is_current, failed→rolledback) or conductor up with a fix (new deploy row, prior failed→superseded).

↪ How cold start, placement, and is_current flips actually behave

Cold start. A fresh deploy (zero target replicas observed) isn't a separate branch — it falls through the three "new replica" gates because each is an existential check: any crashed → none; any lost its host → none; all healthy → vacuously true with zero replicas. The flow lands at the count gate (count new vs desired_count), which sees below. Because outgoing is empty there's no old version to protect, so it batch-creates all desired − current replicas in one tick instead of +1. The +1 surge throttle only applies while outgoing > 0 (a rolling update draining an old version); with nothing to keep serving, serializing would be pure latency. The same shortcut covers a plain scale-up of an already-running version.

Create and assign are one atomic action. IntentCreate commits CreateReplica + AssignReplicaHost in a single WithReconcileTx: the scheduler bin-packs a host during the decide phase, then creates the row and reserves the host together under the host.revision CAS. So a replica is born already placed — host_id is never NULL from the create path, and pending → scheduling collapse to an instant (it lands in starting). If the chosen host was grabbed first → ErrConflict rolls the whole tx back, nothing is created, retry next tick; if no host fits at decide time, the create just isn't emitted this tick.

A replica only goes host-less by losing its host afterward — the host dies/drains, or a shifting migration. That's the one case host_id NULL appears, and the re-placement gate (REPLACE → IntentAssign) handles it: re-bind the existing row to a new host, no re-create. It sits right after the crash gate so lost capacity is restored before health/counts are evaluated, and it self-resolves the moment a host frees up or joins.

is_current flips at conductor up, not after the new version is healthy. From the very first tick the new deploy is is_current=true (the target) and the prior deploy is is_current=false (outgoing). During a failed rollout the new deploy stays is_current=true · status=failed while the outgoing (is_current=false) replicas keep serving — the drain gate never opened, so old traffic is never cut. conductor rollback is the only thing that flips is_current back.

Drain is all-at-once; create is one-at-a-time. The RDRAIN → RID branch drains every outgoing replica still in active in a single tick (all → draining, status=draining), and they reap together after drain_seconds. That's safe because RID is only reached once the health gate and the count gate have both passed — the full new version is already up and serving, so complete replacement capacity exists. The create side is deliberately the opposite: while an outgoing version still exists it ramps +1 per tick (surge=1), so a broken new version trips its health check or crashloop at replica 1 — blast radius 1 — before the engine commits to all N. Cautious ramp-up, decisive drain. (Batch-create-all applies only at cold start / scale-up, when there's no outgoing to protect.)

＋ What this gate machine adds beyond a pure N→N+1 rollout

The original rollout-strategy.md only described version rollouts. A complete v1 reconcile loop also has to handle the steady-state and failure cases below — now folded into the diagram:

  • Scale-down / scale-to-zero. The count gate is now three-way (below / at / above desired). above drains the excess target replicas (IntentDrain → reaped; recreate also releases the volume_lease). Previously every "≠ desired" went to IntentCreate, so lowering desired_replicas would have created replicas forever.
  • Reaping is general, not outgoing-only. Both the excess target replicas from a scale-down (RSHRINK) and the outgoing replicas from a rollout (RID) land in draining and are reaped by the same transition: any replica with drained_at + drain_seconds < now → reaped. It's a per-replica, version-agnostic step — the flowchart draws the reap under the outgoing branch for the rollout story, but a scale-down-drained target replica is caught by the identical rule ({drainWindowElapsed, destroy}). Unconditionally safe, because entering draining already passed the right gate. Status: this reaper lives in the reconcile loop — reconcileIntentsFor is still a stub, so it's designed-not-yet-wired (comments in postgres.go / deployments.sql.go already assume "the reconcile loop reaps the replicas").
  • Progress deadline on the health gate. A new replica that comes up but never goes healthy (and never crashes to trip restart_max) used to wedge the rollout indefinitely. Now health-gate open > progress_deadline trips the deployment to failed · stalled and freezes for the operator — same exit as a crashloop.
  • Status bookkeeping. The loop now writes status = draining when it starts draining outgoing, and active / failed at their terminals. The remaining transitions are set outside this loop: pending + the prior deploy's superseded at conductor up, and rolledback at conductor rollback.

Still deliberately out of v1: per-deployment speed knobs (canary, maxSurge/maxUnavailable), manual single-replica restart, and automatic rollback.

The same gate machine, as a rule table in code

That branchy flowchart collapses to a flat, inspectable table. A rule is a guard + action pair — the same mechanism as the abort gates; only the action's outcome differs (gate → halt, rule → emit). Two things keep it uniform across the group/replica split:

  • A scope tag — group rules run once per group; replica rules run per replica. Without it, a group rule like createDeficit would fire once per replica and over-create.
  • emit returns []Intent — so a group rule can emit the whole create deficit (desired − healthy) in one shot, while most replica rules emit one.
// One rule = guard + action — the same mechanism as the abort gates.
// Only the action differs: a gate halts, a rule emits intents.
type scope int
const ( ScopeGroup scope = iota; ScopeReplica )

type rule struct {
    scope scope
    when  func(c ctx) bool
    emit  func(c ctx) []Intent   // []Intent: a group rule emits the whole deficit
}

type ctx struct {
    g group     // derived facts: counts, has_outgoing, leases
    r *replica  // nil for group-scoped rules
}

The rolling strategy is then just data — each row tagged with its scope, and (comment) the replica phase that branch drives toward, matching the diagram's tints:

var rollingRules = []rule{
    // group-scoped — run ONCE per group
    {ScopeGroup,   anyCrashedPastMax,  failDeployment},  // → failed
    {ScopeGroup,   belowDesired,       createDeficit},    // → pending ×(desired−healthy)

    // replica-scoped — run PER replica, first match wins
    {ScopeReplica, pendingPlacement,   scheduleOnHost},  // → scheduling
    {ScopeReplica, healthyAndCurrent,  promoteToActive}, // → active
    {ScopeReplica, outgoingNewHealthy, drain},           // → draining
    {ScopeReplica, drainTimerElapsed,  destroy},         // → reaped
}

The engine is two passes over that one table — group-scoped once, replica-scoped per replica with first-match-wins — feeding the clamp (stage 6) afterwards:

func evalRolling(g group) []Intent {
    var out []Intent

    // 1 · group rules — once
    for _, rl := range rollingRules {
        if rl.scope != ScopeGroup { continue }
        c := ctx{g: g}
        if rl.when(c) { out = append(out, rl.emit(c)...) }
    }

    // 2 · replica rules — per replica, first match wins
    for i := range g.replicas {
        c := ctx{g: g, r: &g.replicas[i]}
        for _, rl := range rollingRules {
            if rl.scope != ScopeReplica { continue }
            if rl.when(c) {
                out = append(out, rl.emit(c)...)
                break  // one action per replica per tick
            }
        }
    }
    return out
}

↪ Scope by the action's reach, not the guard's

failDeployment's guard reads a single replica (restart_count > restart_max) but its effect is group-wide. So it's a group rule with an existential guard (any) — emitted once, not once per crashed replica. The cold-start / scale-up shortcut falls out for free: with outgoing empty, createDeficit emits all desired − healthy at once; the +1 surge throttle lives in the clamp, not the rule.

The full cascade, in priority order — 1:1 with the gate machine

The teaching table above is the shape; this is the faithful encoding. Because the diagram takes one branch per group per tick, it's a single per-group ordered cascade, first-match-wins — so row order alone carries every precedence (CRASH before HEALTH before count before drain). Two effects fall out for free, no special type needed: hold = a row that emits nothing; fail = a row that emits a status=failed write (the freeze is the next tick's precondition gate). Comments tag the diagram node + target phase.

// stateful = false · per-group cascade · first-match-wins · one branch / tick.
var rollingCascade = []rule{

    {newNotAllHealthyYet,           hold},                       // HEALTH  → emit nothing, end tick

    {belowDesired,                  createOneSurge},            // rolling surge +1
    {aboveDesired,                  drainExcessTarget},         // scale down

    {outgoingStillInActive,         drainOutgoing_setDraining}, // RDRAIN  → draining
    {outgoingDrainWindowElapsed,    destroyDrained},            // RWIN    → reaped
    {allOutgoingReaped,             setActive},                 // RALL    → active

// stateful = true · drain-before-lift · surge = 0 (single-writer volume).
var recreateCascade = []rule{
    {anyNewCrashedPastMax,          emit(deployFailed)},        // CRASH
    {anyNewLostHost,                reassignHostless},          // REPLACE
    {newHealthOpenPastDeadline,     emit(deployStalled)},       // PROG
    {newNotAllHealthyYet,           hold},                       // HEALTH

    {outgoingStillInActive,         drainOutgoing_setDraining}, // RCDRAIN → draining
    {outgoingDrainWindowElapsed,    destroyDrained},            // RCWIN   → reaped
    {anyOutgoingNotReaped,          hold},                       // lease still held → wait
    // ── volume free → lift the new version ─────────────────────
    {belowDesired,                  createDeficitWithLease},    // RCCREATE
    {aboveDesired,                  drainExcess_releaseLease},  // RCSHRINK
    {atDesired,                     setActive},                 // RCDONE
}

The engine picks the array by the stateful flag (the diagram's SF split) and walks it first-match-wins — that's the entire decide step for one group:

func reconcileGroup(g group) []Intent {
    cascade := rollingCascade
    if g.stateful { cascade = recreateCascade }   // SF

    for _, rl := range cascade {
        if rl.when(g) { return rl.emit(g) }   // first match wins → one branch / tick
    }
    return nil                                  // nothing matched ⇒ steady state, hold
}

↪ Why ordering is the whole design

Every "at desired / else" in the diagram is just falling through to the next row: not-below and not-above means we're at desired, so the create/drain-excess rows miss and the retire rows run. Move newNotAllHealthyYet below the count rows and you'd drain the old version before the new one is healthy — an outage. The precondition gates (stale / frozen / cordoned) are not in this array; they're the order-irrelevant AND-filter that runs before reconcileGroup is ever called.

⑨Losing races safely — optimistic concurrency

The decision reads run outside the write tx, so the placement is computed against a snapshot that may already be stale by commit time. Three guards catch every stale write; any of them returns ErrConflict, which rolls back the whole placement — the next tick recomputes from fresh state. No lock-holding across decisions.

Host filled up

Bin-packing saw free capacity, but another placement grabbed it first.

CAS on host.revision

AssignReplicaHost reserves iff host.revision == expected; moved → ErrConflict.

Sensor wrote first

Scheduler decided a phase at rev 5, but the Sensor already advanced it to rev 6.

CAS on replica.revision

SetReplicaPhase writes iff revision == expected; stale decision is dropped, not clobbered.

Lease contested

Two replicas try to claim the same stateful volume.

PK on volume_id + upsert WHERE

AcquireVolumeLease — only one wins; the other gets 0 rows → ErrConflict. expires_at fences the old writer.

ReconcileTx — the writes that must commit together

Schedule + reserve (no orphan replica, no double-booked host) and the stateful single-writer lease all land in one short tx. Any error — including a lost CAS — rolls the whole placement back.

⑩Why it converges

Self-healing

Delete a replica row by hand → next tick sees desired > observed → recreates it. Nothing remembers the old state; the gap is the instruction.

Restart-safe

Control plane crashes mid-reconcile? Writes were CAS-guarded and atomic. Next tick re-derives everything from the DB snapshot and re-converges. No journal to replay.

Idempotent intents

Same intent applied twice is safe — same-phase writes no-op, the composite FK rejects undeclared (deployment, region) targets, and lease upserts are guarded.

Bounded blast radius

A lost race never corrupts state — it just drops one placement decision. The slowest possible outcome is "try again in 2s," never divergence.
