Railway CLI — driving the orchestration engine

CLI Examples

How a user expresses intent — and how the CLI figures out which project/service to patch.

The idea in one line: every command resolves a (project, environment, service) target — flags → env var → linked directory → prompt — then sends a declarative patch to desired state. None of them take a path to a config file; the only path anywhere is the optional [path] to your code in up.

1Linked directory context — the everyday case

Link once per directory; every later command just knows the target.

~/projects/my-api — bash
$ cd ~/projects/my-api $ railway link # one-time, interactive picker ✓ Linked to project=my-api env=production service=api # …writes the link into ~/.railway/config.json, keyed by this dir $ railway up # no flags — resolves from the link → deploying my-api / production / api $ railway scale eu-west=2 # same dir → same context → scaling my-api / production / api

2Explicit flags — override or scripting

Flags win over everything — useful when one repo touches several services.

bash
$ railway up --service api --environment production → deploying my-api / production / api $ railway scale us-east=3 --service worker --environment staging → scaling my-api / staging / worker # ignores any link $ railway logs --project 1234-abcd --environment production # -p requires -e (a project id needs an env to be unambiguous)

3Environment variables — how CI works

The token itself identifies the project, so CI never needs railway link.

ci-runner
# no interactive login, no linked directory: $ export RAILWAY_TOKEN=<project-token> # stored in CI secrets $ railway up --ci → token scopes it to exactly one project/env — no link, no prompt

4Interactive prompt — nothing resolved

~/brand-new-folder — bash
$ cd ~/brand-new-folder $ railway up ? No linked project found. Select a project: › ❯ my-api billing-svc scratch # …then asks env, then service — and offers to save the link

5The three "json / path" things (easy to conflate)

ThingWhat it isIdentifies the project?
up [path]path to the code dir to tarball & upload❌ no
~/.railway/config.jsonthe link: dir → project/env/service, + auth token✅ this one
railway.json (repo)deploy config-as-code (replicas, healthcheck…)❌ optional; configures, doesn't identify
bash
# (a) the PATH arg in `up [path]` = which CODE to upload (not a config) $ railway up ./backend # tarball & deploy the ./backend dir $ railway up # tarball & deploy "." (cwd) # (b) ~/.railway/config.json = the LINK + auth token (answers "which project?") $ cat ~/.railway/config.json { "projects": { "/Users/me/projects/my-api": { "project": "my-api", "environment": "production", "service": "api" } }, "user": { "token": "•••" } } # (c) railway.json in the repo = DEPLOY config-as-code (optional, not identity) $ cat railway.json { "deploy": { "numReplicas": 2, "healthcheckPath": "/health", "region": "us-west1" } } $ railway up # uploads code; reads these settings; identity still from (b)

6Full session — tying it together

~/projects/my-api — bash
$ cd ~/projects/my-api $ railway link # (b) link written $ railway up # identity ← link; deploy cfg ← railway.json; code ← "." → my-api/production/api, 2 replicas in us-west1, health=/health $ railway scale us-west1=4 # patches replicas → 4 (same context) $ railway variable set LOG=debug # patches env (same context) $ railway logs # reads observed state (same context)
How it maps to the engine: the CLI's whole job is to resolve a (project, env, service) identifier, then send a mutation (e.g. EnvironmentPatchCommit) that patches one field of desired state for it. The reconcile loop does the rest. Deploy / scale / rollback / self-heal are the same loop reacting to a patched field — see the ERD §13–14.

7Worked scenario — rxlog-platform, two environments

A real run: rxlog-platform is a Laravel app, so we deploy it as a web service + a postgres service, across production and staging. After each command, watch the two server-side desired-state records diverge — that is where config lives; the commands just patch it.

Step 1 — create the project, add services, declare compute (config-as-code)

~/Documents/rxlog/rxlog-platform — bash
$ cd ~/Documents/rxlog/rxlog-platform $ railway init # create project "rxlog-platform" (+ default env "production") $ railway add --service web # the Laravel app (this repo) $ railway add --database postgres # a stateful service (gets a volume) $ railway link # pin this folder ✓ rxlog-platform / production / web $ cat railway.json # compute requirements, committed with the code { "build": { "builder": "DOCKERFILE", "dockerfilePath": "Dockerfile" }, "deploy": { "startCommand": "php artisan serve --host 0.0.0.0 --port $PORT", "numReplicas": 1, "healthcheckPath": "/up", // Laravel's built-in health route "restartPolicyType": "ON_FAILURE" } }

Step 2 — make a second environment

bash
$ railway environment new staging # clones the services into a new env ✓ staging created — now has its own web + postgres (separate config + data)

Two environments now exist, each an independent copy. Same folder — we'll switch between them with railway environment.

Step 3 — set production state & deploy

bash
$ railway environment production # select which env we're editing $ railway variable set APP_ENV=production LOG_LEVEL=warning -s web $ railway up -s web # build → COMMIT desired state → reconcile → rxlog-platform/production/web: image=img@a1, replicas=1, health=/up ✓ healthy $ railway scale us-west1=3 -s web # prod needs headroom → patch replicas 1→3 · reconciler starts 2 more · ✓ 3/3 $ railway volume add -s postgres --mount /var/lib/postgresql/data # no --size flag → vol-prod created · pinned to a us-west host · lease → postgres size: capped by plan (Pro=50GB), live-resizable later — NOT set at create time
server-side desired state · rxlog-platform / production
web = { image:img@a1, replicas:3, region:us-west1, env:{APP_ENV:production, LOG_LEVEL:warning}, health:/up } postgres = { image:postgres:16, replicas:1, volume:vol-prod }

Step 4 — set staging state (smaller, debug) & deploy

bash
$ railway environment staging # SWITCH — now editing staging's records $ railway variable set APP_ENV=staging LOG_LEVEL=debug -s web $ railway up -s web → rxlog-platform/staging/web: image=img@a1, replicas=1, health=/up ✓ healthy $ railway volume add -s postgres --mount /var/lib/postgresql/data → vol-stg created — SEPARATE disk + data from prod (same plan-based cap) # staging stays at 1 replica — cheaper. No scale command needed.
server-side desired state · rxlog-platform / staging
web = { image:img@a1, replicas:1, region:us-west1, env:{APP_ENV:staging, LOG_LEVEL:debug}, health:/up } postgres = { image:postgres:16, replicas:1, volume:vol-stg }

Same code (img@a1), but the two records have already diverged: replicas 3 vs 1, different vars, different volumes/data.

On volume size: Railway's volume add has no --size — the max is set by plan tier (Trial 0.5GB · Hobby 5GB · Pro 50GB, self-serve to 1TB) and you resize live later. In design terms: a volume's size is a mutable property you patch (another desired-state field + a reconcile, like scale), not a fixed create-time argument.

Step 5 — change state again: traffic spike on prod, ship new code

bash
$ railway environment production $ railway scale us-west1=6 -s web # spike: 3 → 6 → patch replicas 3→6 · reconciler fans out 3 more · ✓ 6/6 # new code: ship to staging first, verify, then prod (zero-downtime rollout) $ railway environment staging $ railway up -s web → staging/web image=img@a1 → img@b2 · health-gated · ✓ $ railway environment production $ railway up -s web → production/web img@a1 → img@b2 · start 6 new, health-gate, drain old · ✓ 6/6 on b2

Step 6 — scale staging to zero overnight (cost)

bash
$ railway environment staging $ railway down -s web # replicas → 0 (postgres + its volume/data untouched) → staging/web replicas 1→0 · containers drained · data on vol-stg preserved

Where it all landed — the two records, side by side

rxlog-platform / production
web = { image:img@b2, replicas:6, region:us-west1, env:{APP_ENV:production, LOG_LEVEL:warning}, health:/up } postgres = { replicas:1, volume:vol-prod }
rxlog-platform / staging
web = { image:img@b2, replicas:0, region:us-west1, env:{APP_ENV:staging, LOG_LEVEL:debug}, health:/up } postgres = { replicas:1, volume:vol-stg }
The whole point, in one read: there are two independent desired-state records living server-side (one per environment). Every command just patched one field of one record — up→image, scale→replicas, variable set→env, down→replicas:0, volume add→volume. railway environment only chose which record you were editing. The reconcile loop continuously drives each record's reality to match. You never start a container by hand — you commit a desired state and the engine converges.
