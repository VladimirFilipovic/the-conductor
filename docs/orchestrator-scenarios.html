The Conductor Orchestrator

A reconcile engine that takes a user's desired state for a service and continuously works to make reality match — scenario by scenario, here is everything it must cover.

desired state
what the user asked for: deployments (the current commit) + deployment_regions (region → count). Written by the CLI.
observed state
what is actually running: replicas (healthy, observed phase) + hosts (capacity, heartbeat). Written by the observer — a sensor loop that only ingests truth (§3).
reconcile
the controller loop that reads both, computes the diff, and takes one step toward closing it — then repeats, forever. Separate goroutine from the observer; they meet only in Postgres.
level-triggered
each tick re-derives intent from the database; it never trusts memory of the last tick. This is what lets it survive restarts.

1 · The one idea

Every entity stores a desired and an observed half — and that split runs all the way down to the actor that writes each half. The controller (reconciler) owns intent; the observer owns truth. Closing the gap between them, on every tick, without assuming it remembers anything — that single property, level-triggered convergence, is what makes it self-healing and restart-safe.

desired (controller writes)               observed (observer writes)
  deployments (is_current) ............... replicas (healthy, observed phase)
  deployment_regions {region: N} ......... hosts (capacity, heartbeat, status)
  volumes (desired_size) ................. volumes (observed_size), volume_leases

replicas straddles both — intent half (controller) vs truth half (observer):
  replicas (desired_status, host_id) ..... replicas (healthy, phase)
Guiding principle. "Each entity stores desired vs observed state. The reconciler's whole job is closing that gap." Read the gap, take the next step, repeat.

The replica's life is a phase machine; the deployment's life is a status machine. The phases are the rollout steps. The machine is co-driven: the controller advances intent phases (it decided to schedule/start/drain), the observer writes the truth phases it confirms from the agent (it actually came up healthy / actually exited). Neither writes the other's, so the two loops never contend on the row.

replica.phase:   pending → scheduling → starting → health_check →
              healthy → shifting → active → draining → reaped
              ^controller intent^        ^observer-confirmed^  ^controller^
replica.healthy: written by the observer only (heartbeat / health_check result)
deploy.status:   pending → active → draining / failed / rolledback / superseded   (controller)

The replica's three state columns

A replica row carries three orthogonal state fields, and the whole self-healing property depends on keeping them separate — each is owned by a different actor and answers a different question.

ColumnWriterQuestionValues
desired_statuscontrollerShould this replica be alive at all?running · stopped
phaseco-drivenWhere is it in its lifecycle right now?pending … reaped / failed
healthyobserverIs it passing health / heartbeat right now?true · false
Why three and not one. The revealing combination is desired_status=stopped + phase=healthy + healthy=true — “running fine, but doomed, drain not started.” No single field can say that. And the restart decision is a clean predicate over all three: desired_status=running AND phase=failed AND restart_count<restart_max → restart.

desired_status — pure controller intent

ValueSet whenWhat it drives
running default on create; the reconciler still wants this slot filled. drives scheduling & start; on an unexpected exit (phase=failed) it is the signal to self-heal (restart under the cap).
stopped reconciler decides the slot must go: scale-down (#3), version superseded (#4), down, or host evacuation (#7/#8). hands the replica to the rollout to drain → reap; an exit now is expected — never restarted.

phase — the lifecycle (entry condition → what it drives)

Controller-intent phases (it decided to schedule / start / shift / drain) and observer-confirmed phases (the agent actually came up healthy / exited) alternate down the row. Neither actor writes the other's, so the two loops never contend.

PhaseWriterEnters whenWhat it should affect / drive
pendingcontroller row just created from a gap (host_id=null). the scheduler must place it. No compute reserved. If nothing fits it stays here with an alloc_reason (#9) — retried, never overcommitted.
schedulingcontroller scheduler bound a host (host_id set under revision CAS). reserves that host's cpu/mem (counts against free capacity); signals the agent on that box to create the workload.
startingcontroller intent / agent agent accepted the task and is pulling image / booting the microVM. workload coming up; not in traffic, healthcheck not yet passing.
health_checkobserver process is up; agent is running the healthcheck probe. the health gate. Pass → healthy; fail past timeout → failed. Still not serving.
healthyobserver healthcheck passed; sets healthy=true. now eligible to serve; unblocks the rollout — only once the new replicas are healthy may the old be drained (#4).
shiftingrollout rollout begins moving traffic onto this (new) replica. traffic cut-over; makes the old version's replicas eligible to drain.
activerollout traffic fully shifted; steady state. the happy idle target; counts as observed toward the desired region count. Loop idles.
drainingcontroller desired_status=stopped, or its host went notready (#7). pulled from traffic; given drain_seconds for in-flight connections; for stateful, the volume lease is released/fenced (#12).
reapedcontroller drain window elapsed and connections closed. workload stopped, host capacity freed, row removed; observed count drops by one.
failedobserver / rollout crash, missed heartbeat, or healthcheck failed past timeout. terminal & surfaced. If desired_status=running and restart_count<restart_max → reconciler restarts with backoff (#6); past the cap it rests here — no hot-loop.

healthy — observer-only truth

A single boolean the observer writes from heartbeats / healthcheck results, never the controller. It is deliberately decoupled from phase so liveness can tick on its own fast cadence (§3): true when a fresh signal confirms the replica is serving; false the moment a heartbeat is missed or a check fails — which, on a desired_status=running replica, is exactly what arms the self-heal path.

3 · Actors & system shape

Only two things run forever: a controller loop (reconciler) and a sensor loop (observer). They never call each other — Postgres is the only wire between them. Everything else is either invoked by the controller (scheduler, rollout) or lives out on the fleet (the agent, the one actor that touches reality).

        ┌─────────────────────────────────────────────────────────┐

Two loops, one bus. The controller writes intent; the observer writes truth; they meet only in Postgres.

Why split sensor from controller. Independent cadence (heartbeats tick fast, reconcile slower); failure isolation (if the controller stalls, status stays truthful — and scenario 7 host-down detection only works because liveness is an independent signal); and it's free to split into two processes later, since the contract is DB columns, not function calls. Both loops guard writes with the revision CAS (scenario 14).

Scheduler vs Rollout orchestrator — decision, not action

Both are invoked by the reconciler — neither is its own loop, and crucially neither ever calls a host. They write intent into Postgres; the host agent reads that intent and is the one that touches reality. The split between them is placement (where) vs sequencing (in what order, safely).

SchedulerRollout orchestrator
QuestionWhere does this replica go?In what order & timing, safely?
Shapeone-shot, stateless decisiona sequence that unfolds over ticks
Inputan unplaced replica (host_id = null)a set of replicas mid-transition (old vs new commit)
Stepsfilter → score → bindstart → health-gate → shift → drain → reap

Scheduler — placement (filter → score → bind)

filter
narrow the fleet to eligible hosts: same region, status=ready (skip cordoned/draining/notready), enough free cpu/mem, and for stateful enough disk_bytes for the volume.
score
rank the survivors — bin-pack tightest-fit (least free capacity that still holds it) to keep the fleet dense, optionally spread for resilience.
bind
write replicas.host_id + alloc_reason, guarded by the host's revision CAS so two concurrent binds can't double-book the same capacity (scenario 14).
output
exactly one thing — a chosen host on a replica row. If nothing fits, the replica stays pending with an alloc_reason (scenario 9); it is retried, never overcommitted.

Rollout orchestrator — sequencing over time

stateless — surge
start the NEW replicas alongside the old → health-gate → shift traffic → drain old for drain_seconds → reap. New never goes healthy → stop it, leave old serving, mark failed (scenario 4).
stateful — handoff
no overlap, because a volume admits exactly one writer: drain old pg-0 → release/expire its volume_lease (fencing) → new acquires the lease → attach → start → health-gate (scenario 12).
what it owns
the order, the timing (durable timers for drain windows), and the safety gates (don't drain old until new is healthy; don't start the new writer until the old lease is released). Placement of any new replica it delegates back to the scheduler.
why separable
plain Go loop now; the per-step retries, durable timers, and rollback compensation are exactly what Temporal absorbs later (§7) — keyed by deployment_id.
The chain. reconciler (what's the gap) → scheduler (where) → rollout (in what order, safely) → it all lands as intent in Postgres → host agent (actually do it) → observer writes back the truth. Three of the four only ever decide; one acts.

The crash (chaos) and the user's scale drive the reconciler down the same code path — it never asks why observed ≠ desired, only closes the gap.

4 · The scenarios

Each is framed as trigger → the gap → what the engine does. Tags mark the build phase: v1 stateless first slice, next rollout & fleet, stateful the hard tail.

1 · Initial deploy: 0 → N v1

trigger
up writes a current deployment + {us-east-1: 3}.
gap
desired 3 replicas, observed 0.
engine
create 3 replicas (ordinals 0–2) → bin-pack each onto a ready in-region host → start → health-gate → active; mark deployment active.

2 · Scale up: N → N+M v1

trigger
scale us-east-1=5, or an up with a higher count.
gap
desired 5, observed 3.
engine
create 2 more, schedule + start; the existing 3 untouched.

3 · Scale to zero / down: N → 0 v1

trigger
down, or scale region=0.
gap
desired 0, observed 3.
engine
drain then reap all replicas. Volumes are preserved — only compute stops; the service and deployment rows remain.

4 · New-version rollout (stateless) v1 next

trigger
up with a new image/config; old commit → superseded.
gap
observed replicas point at the old deployment; desired is the new one.
engine
surge: start NEW alongside old → health-gate → shift traffic → drain old (drain_seconds) → reap. New never healthy → stop, leave old serving, failed.

5 · Rollback — desired half done engine: next

trigger
conductor rollback [--to vN] re-points is_current to an older deployment (old → rolledback, target → pending).
gap
same as a rollout, but the target image already exists — no rebuild.
engine
identical convergence as #4, toward the re-pointed version.

6 · Replica crash → self-heal v1

trigger
a replica exits or fails its health check (healthy=false).
engine
restart with backoff, bumping restart_count, capped at restart_max; past the cap → failed, surfaced, no hot-loop.
note
this proves the loop is level-triggered: delete a replica row and the next tick recreates it.

7 · Host failure → reschedule next

trigger
hosts.last_heartbeat goes stale → mark notready.
engine
its replicas are presumed dead → reschedule onto other hosts. Stateful needs the volume reachable first.

8 · Host drain / cordon (maintenance) next

trigger
operator sets draining / cordoned.
engine
cordoned = no new placements here; draining = evict existing replicas elsewhere, then the box is safe to pull.

9 · No capacity / unschedulable v1

trigger
desired replicas exceed free fleet capacity in-region.
engine
replica stays pending with an alloc_reason; never overcommit. Placed automatically once capacity frees.

10 · Multi-region spread next

trigger
{us-east-1: 3, eu-west-1: 2}.
engine
reconcile each region independently; a region with no capacity stays pending without blocking the others.

11 · Stateful placement + volume provisioning stateful

trigger
add --database then up for a stateful service.
gap
the single replica (pg-0) needs its volume before it can run.
engine
provision the volume, place it by disk_bytes, pin replicas.volume_id; placement is disk-aware, not just cpu/mem.

12 · Stateful rollout / failover → volume handoff stateful

trigger
new version, or the host holding pg-0 dies.
constraint
exactly one writer per volume — the volume_leases primary key is the physical guarantee.
engine
handoff, no surge: drain old pg-0 → release/expire its lease (fencing) → new pg-0 acquires the lease → attach → start → health-gate. No surge because a volume admits exactly one writer; a stateful service is one replica, so there is no next ordinal.

13 · Volume resize (grow-only) stateful

trigger
desired_size_bytes raised.
engine
grow the disk, reconcile observed_size_bytes up. Never shrink.

14 · Control-plane restart / concurrency v1

trigger
the engine restarts mid-work, or two ticks overlap.
engine
re-derive everything from the DB each tick (no in-memory truth); guard every write with the revision column (optimistic concurrency). All steps idempotent.
⚠ Hazard the revision CAS does not cover — double-create on overlapping ticks. Two ticks both read “desired 3, observed 0” and each create 3 → 6 replicas. The revision column guards per-row updates (the scheduler binding host capacity); it does nothing for inserts — CAS cannot guard the cardinality of a set you are about to grow. So capacity binding is safe; the create/diff step (scenario 1) is not, on its own.

Mitigations, cheapest-correct first:

GuardWhatWhen
Don't overlap ticks v1 a plain level-triggered loop that finishes one tick before starting the next, plus a single reconciler (leader-elected if ever >1). free, and enough on its own — this is what §7's plain Go loop buys you.
Advisory lock per deployment multi-instance pg_advisory_xact_lock(hashtext(deployment_id)) inside the reconcile txn — locks the right to reconcile this deployment, auto-released on commit. belt-and-suspenders once you run more than one reconciler.
Idempotent insert hard guarantee a deterministic per-slot key + UNIQUE (deployment_id, region, slot), then INSERT … ON CONFLICT DO NOTHING; even a raced double-tick can't duplicate. only if you need hard idempotency over lock-based serialization — costs a slot column (a small concession to the “fungible, no ordinal” rule).

Rule of thumb: optimistic revision CAS for hot single-row contention (capacity bind); advisory lock or idempotent insert for read-modify-write over a set (count-then-create). Reconciler vs observer never contend — they write different columns by design.

15 · Config-only vs image change v1

note
both are just a new deployments row, so both trigger a rollout (#4). v1 does not special-case "only env changed" — the version bump is the signal.

6 · Build order

1
v1 Stateless steady-state. Scenarios 1, 2, 3, 6, 9, 14: replica CRUD, host-capacity query, bin-packer, poll loop, simulated executor. Proves convergence + self-heal; status shows real numbers.
2
next Rollout & fleet. Scenarios 4, 5, 7, 8, 10: version transitions (surge/drain), host liveness, multi-region.
3
stateful Volumes, leases, handoff. Scenarios 11, 12, 13. The hard tail: disk-aware placement and the single-writer protocol at once.

7 · The open decision: A vs B

One choice gates the engine's shape — how the reconcile loop runs.

OptionWhatVerdict
A · Plain Go loopone process polls desired vs observed and convergesrecommended for steady-state — it is already level-triggered via Postgres
B · Temporal workerdurable workflow drives the rollout choreographylater only for the rollout state machine (#4/#12), kicked off keyed by deployment_id
Trade-off. Don't take the Temporal dependency up front. Steady-state convergence wants a plain level-triggered loop; Temporal earns its keep only when the in-flight surge/drain sequencing (durable timers, per-step retries, rollback compensation) gets unwieldy.
